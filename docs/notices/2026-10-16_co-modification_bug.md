# 連絡: CC4M の co-modification 解析のバグについて (2026-10-16)

CC4M のパイプラインで, コミット間の変更行を求める処理にバグがありました.
2026-10-16 に修正済みです. 次のどれかに当てはまる研究は, 結果に影響している可能性があります.

- `src/modules/collect_datas.py` の `find_moving_lines` / `parse_diff_str` を使っている.
- `dest/moving_lines/`, `dest/modified_clones/`, `dest/csv/` の出力, またはそこから作った
  `enriched_fragments`, `scatter`, `clone_metrics` の co-modification 情報を使っている.
- 同じ書き方 (`新しいコミット.diff(古いコミット)` を `"@@"` で split して先頭 hunk だけ読む) を
  別のコードにコピーしている.

## 何が起きていたか

1. 各ファイルの diff のうち, 先頭の hunk しか解析していなかった.
   train-ticket の merge ウィンドウ 43 個では, hunk 全体の 43% (4,814 個中 2,060 個) が無視されていた.
2. hunk ヘッダ行の残りを context 行として数えていたため, 行番号が +1 ずれていた.
3. diff の向きが逆で, 古い側にしか無い行を, 新しい側の挿入行として扱っていた.

その結果, 行の対応付けとクローン断片の「変更あり / なし」の判定が崩れていました.
例えば train-ticket の Order.java (9 サービスのクローンセット) では,
実際にクローン範囲の中が編集されたのは 2 つなのに, 範囲外で行がずれただけの別の 6 つを「変更あり」と判定していました.

## 影響の傾向

- co-modification は全体として少なく出ている可能性が高い (2 番目以降の hunk の変更が拾われない).
- 一方で, 範囲外の変更による行のずれを「変更あり」と誤判定するケースもあるため,
  個々の co-modification 事例は誤検出の可能性がある.
- サービス間とサービス内の比較のような相対比較でも, 両者で誤りの出方が同じとは限らないため,
  再計算して確認するのが安全.

## 確認と対応の方法

1. 使っているコードが 2026-10-16 の修正 (`src/modules/moving_lines.py` の追加) より前のものか確認する.
2. 修正後のコードで, `collect` 以降のステップを再実行する.
   旧形式の `dest/moving_lines/*.json` は自動的に再計算される.
   `dest/modified_clones/` は各ステップの実行時に作り直される.
3. 再計算の前後で, 主要な数値 (co-modified なクローンペア数など) を比べる.

詳細な経緯と検証結果は `docs/PROGRESS.md` の 2026-10-16 のエントリ,
修正後の仕様は `docs/line_tracking.md` を参照してください.
